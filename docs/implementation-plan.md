## 2. 各マイルストーン

### M0 土台（S）

- npm workspaces、TypeScript 7、Vitest 5、Vite 8（mahjong-sensei と同じ版）。`packages/format`・`packages/runtime` の空の枠
- GitHub Actions：型検査・テスト・ランタイムの容量検査（gzip 後 10KB 以下）。PR ごとに動かす
- **Pages の出力を `dist` に切り替える**（`index.html` と `analysis-demo/` を `dist` に写すだけの小さなビルド。M3 ではビルドの中身を足すだけにする）。リポジトリ直下を公開したままだと、録音の wav をコミットした時点で公開側に出て、公開側の容量を無駄に使うため（公開されること自体は構わない：Ao）
- 録音の置き場所を `recordings/` に決め、`dist` には写さない。CI で「`dist` に `recordings/` と `.wav` が無い」ことを確かめる（ゲームに配る wav は、ゲーム側のリポジトリに書き出して置くもので、Pages の対象ではない）。`analysis-demo/` と `index.html` の中身は変えない
- `CLAUDE.md` を置く（日本語、コミット接頭辞、テストの書き方）。mahjong-sensei の「期待値は独立した根拠から書く」を引き継ぐ

**成果物**：CI が緑の空のモノレポ。
**完了条件**：`npm test`・`npm run typecheck` が通り、容量検査と「`dist` に `recordings/` と `.wav` が無い」検査が（空でも）動く。Pages のプレビューで、これまでと同じ URL（`/` と `/analysis-demo/`）が開ける。

### M1 データ形式とランタイム（M）

提案書 4 章のとおり。

1. `format`：型、検証（壊れた JSON を拒否）、正規化（既定値を埋める）、縮小（既定値と `id` を落とす）、版の移行の枠
2. `runtime/compile`：score ＋ 呼び出しの opts ＋ 乱数 → 予定表。Web Audio を触らない純粋な関数
3. `runtime/render`：予定表 → Web Audio のノード。共有の雑音・残響・コンプレッサー、同時発音数の上限
4. `sample` 層：wav（URL か AudioBuffer）を鳴らす層。`ready` が参照先の wav を読み込む（`fetch` ＋ `decodeAudioData`）。音ごとに JSON か wav かを選べる。10KB の目標に収まるように実装する
5. 公開 API：`createSfx(bank, opts)`、`play(name, { pan, gain, delay })`、`installUnlock`、`setMasterGain`、`ready`、`playScore`、乱数の差し替え
6. テスト：compile は手計算の期待値（`tune: 1200` で周波数 2 倍、`beat` と `bpm: 120` で 1 拍 0.5 秒、指数減衰の終点）。render は Vitest のブラウザモード（Chromium）で OfflineAudioContext に描画し、長さ・最大音量・NaN・割れを確かめる。容量検査

**成果物**：`packages/format`、`packages/runtime`。
**完了条件**：提案書 4.1 の `discard`・`kan`・`win` の例が描画でき、`sample` 層の音（短い wav）も同じ API で鳴り、gzip 後 10KB 以下。`reverb` に早期反射（時刻と強さの配列、任意）を足すかを決めている（5e が使う）。

### M2 mahjong の 16 音を移す（M）

1. 現在の `sfx.ts` の合成部分を、乱数を差し替えられる形にして `test/fixtures` に写す（基準）
2. 16 音を `sfx-bank` の JSON に書き直す
3. 聞き比べの道具：同じ乱数の種で基準と新形式を描画し、5ms ごとの音量の推移・スペクトル重心・長さの差を数字で出す（M4 の分析と同じ測定を後で使い回す）
4. Ao が耳で A/B（ブラウザで 16 音を順に鳴らす簡易ページ）
5. mahjong-sensei 側の PR：`sfx.ts` の合成部分をランタイムに置き換え、`soundForEvent`・音量の保存・`gameEvent` は残す

**成果物**：`bank/mahjong.sfxbank.json`、聞き比べの報告、mahjong-sensei の PR。
**完了条件**：数字の差が許容内（M2 で決める）で、Ao が「同じに聞こえる」と判断する。ここで形式の不足が見つかったら、M1 に戻って形式を直す。

### M3 最小のエディタ（L）

- `web/`（Vite）。ピアノロール（置く・動かす・伸ばす・消す、秒とミリ秒の目盛り）、トラック、音色エディタ（層・エンベロープ・フィルタ・ピッチ変化・雑音）、再生・停止・ループ、元に戻す／やり直し、JSON の読み書き、プリセット
- 再生にはランタイムを使う（エディタとゲームで同じ音）
- iPad のタッチ操作
- M0 で作った `dist` のビルドに、エディタを足す
- 画面の文言は mahjong-sensei の規則に合わせる（飾りの文・操作の説明文を置かない、定番の操作はアイコン）

**成果物**：Pages で開けるエディタ。
**完了条件**：M2 の 16 音のうち 3 つ（`discard`・`win`・`riichi`）を、エディタ上で開いて直して鳴らし、JSON に書き出せる。

### M4 分析の TS 化と Claude 連携（貼り付け版）（M）

1. `analysis` パッケージ：`analysis-demo/app.js` の FFT・特徴量を TypeScript に取り出す。テストは**既知の信号**で書く（440Hz の正弦波は重心が 440Hz 付近、インパルスは立ち上がりが最速、など）
2. 効果音向けの指標を足す：立ち上がり（ミリ秒）、余韻の長さ、音の硬さ（重心と高域の比）、音量の山、長さ。短い音では調・和音進行を出さない
3. 記号の分析（音符から）：音域・密度・音階の候補・和音の候補（M6 の後に拡張）
4. 要約の形式 `analysis-report/1`：80 行以内、上位の指摘を数個まで（mahjong-sensei の summary と同じ考え方）
5. 変更案の形式 `sfx-patch/1`：音符・層・パラメータの差分（`id` で指す）。適用・取り消しの関数とテスト
6. エディタ側：要約をコピーする、貼られた差分を適用する、A/B で聞き比べる（C5）
7. 既存のデモはこの `analysis` を使う側に置き換える（動作は変えない）

**成果物**：`packages/analysis`、`sfx-patch/1`、エディタの分析パネル。
**完了条件**：要約を Claude に貼る → 差分が返る → 適用して A/B で聞ける、までが手で一通りできる。

### M4.5 軽量化：周波数解析による変換（M）

提案書 6 章。**物理エンジンより先に作る。** 「既知の層から作った音を当てはめて、元の層が戻るか」を確かめられるので、正解が分かる状態で精度を測れる。5d はこの機能を物理の録音に使うだけになる。

1. `analysis` に STFT（M4 で取り出した FFT）と、聞こえ方の距離（マルチ解像度のスペクトル距離＋立ち上がり・長さ・音量の山の差）を足す
2. `fit`（新しいパッケージ `packages/fit`）：持続するピークの検出 → 周波数・減衰・強さの推定（A）
3. 残差から帯域包絡 → 帯域雑音の層（D）、全体のエンベロープの当てはめ
4. 予算（バイト数・ノード数）を指定して、寄与の小さい層から外す（F）。量子化と整理（G）
5. 測定：`discard`・`sticks`・`win` の 3 音で、元と変換後の大きさ・ノード数・距離を表にする。効果が小さければここで止める（提案書 6.5）
6. 短い衝撃音で周波数の分解能が足りなければ、プロニー法（B）を足す
7. エディタ：読み込んだ wav・録音から「層に変換」し、元との A/B と差の数字を出す

**成果物**：`packages/fit`、測定の表、エディタの変換画面。
**完了条件**：既知の層から作った音で、周波数が ±1%・減衰が ±10% 以内で戻る。3 音の測定の表が出ている。

### M5 物理エンジン（L）

提案書 5 章。4 つに分ける。

- **5a エンジン本体**：2.5D の剛体（球・箱・平面）、反発と摩擦、固定の刻み幅、乱数の種。決定論のテスト（同じ種で同じ接触列）、保存則など手計算できる場面のテスト。出力は接触の出来事（時刻・衝撃の強さ・相対速度・材質）
- **5b 音の生成**：材質ごとのモード（周波数・減衰・強さ）と、接触の強さに応じた励起。接触の出来事 → 減衰する正弦波＋帯域雑音
- **5c 録音と加工**：OfflineAudioContext で AudioBuffer にし、wav で保存（`recordings/`）。ゲームへの書き出しは、JSON・wav・両方から選べる。切り出し・無音除去・正規化・フィルタ・ピッチと長さの変更
- **5d 変換**：物理の録音を M4.5 の `fit` で `layers` の JSON に変換し、元との差を同じ指標で出す（新しい実装は要らない）
- **5e 部屋の反響**：箱形の部屋のモデル（セービンの式の残響時間、鏡像法による早期反射 2 次まで、距離による音量・遅れ・向き）。結果を `reverb` の設定と `pan`・`gain`・`delay` に写す。テストは手計算の期待値（例：幅 5m・奥行き 4m・高さ 3m で全面の吸音率 0.2 なら、体積 60 立方 m・表面積 94 平方 m・吸音の合計 18.8 で、RT60 ＝ 0.161 × 60 ÷ 18.8 ≒ 0.51 秒。壁 1 枚に対する鏡像の経路長と遅れは、幾何から手で出せる）。形式には `reverb` の早期反射（時刻と強さの配列、任意）を足すかを M1 の終わりに決める

最初の題材は「牌が卓に落ちる音」（今の `discard`）。

**成果物**：`packages/physics`、エディタの「物理から作る」画面。
**完了条件**：物理から作った `discard` を M4.5 で変換し、M2 で書いた `discard` と A/B で聞き比べられる。変換後の JSON が 1 音 3KB 以下。

### M6 MIDI（S〜M）

- `midi` パッケージ：標準 MIDI ファイルの読み書き（テンポ変更・ドラムのチャンネルの扱いを決める）
- 読み込み → `sfx-score` の変換、書き出し（音色・雑音は落ちることを明記）
- テスト：既知のバイト列から作った SMF で、ノート数・時刻・テンポが合うこと

**完了条件**：手元の MIDI を読み込んで、エディタで編集・再生・分析できる。

### M7 保存と MCP（L）

- 作品の置き場所（分かれ道 D の D2）：D1（作品・版・タグ）、R2（録音の wav。エディタからの配布の元になる。公開するかは、作品ごとに選べるようにする）。全テーブルに `user_id`（mahjong-sensei と同じ規則）
- MCP サーバ（Workers、`workers-oauth-provider`、Cloudflare Access）。ツール案：`list_sounds`、`get_sound`、`get_analysis`、`save_sound`、`apply_patch`、`get_context`（用途と好みの記憶、C6）
- mahjong-sensei の MCP（#43 まで）と実装を共有するか、写すかを決める。共有するなら先に共通部分を `store` から切り出す
- ランタイムの npm 公開（F3）：ライセンス（MIT 想定）、型定義、README

**完了条件**：claude.ai から作品を読み、変更案を保存でき、エディタで開くと差分が出る。

## 4. 並行して決めること

| 決めること | いつまでに | 推奨 |
| --- | --- | --- |
| ツールとランタイムの npm 名 | **決定（Ao）**：ランタイムは `@sfx-atelier/runtime`。ほかのパッケージも `@sfx-atelier/` を付ける | |
| ogg の書き出し | **決定（Ao）**：要件から外し、音声ファイルは wav のみ（X4 は wav のみ）。配布は wav と JSON の両方に対応 | |
| 物理を 2D・2.5D・3D のどれにするか | **決定（Ao）**：2.5D。部屋の反響は簡単なモデルで入れる（5e） | |
| 録音の wav をリポジトリに置くか | **決定（Ao）**：リポジトリに置いてよい（`recordings/`）。公開されても構わないが、公開側の無駄な容量になるので Pages の公開対象（`dist`）からは外す。配布は wav と JSON の両方に対応。容量の上限とライセンスの記録は M5c までに決める（推奨：上限は 1 ファイル 1MB、出どころとライセンスを `recordings/README.md` に表で残す） | |
| `reverb` に早期反射を足すか | **決定（M1）**：任意の `early`（[時刻, 強さ] の並び、32 個まで）を足した。インパルス応答のその時刻に足すだけなので、ランタイムの容量はほぼ増えない。5e の鏡像法の結果をここに入れる | |
| 2.5D の中身（5a） | **決定（5a）**：位置と速度は 3 次元、回転は鉛直軸まわり（yaw）だけ。箱は傾かず、球は転がらない（滑るだけ）。平面は床（真上の法線）と壁（水平の法線）だけ。材質の組は反発・摩擦それぞれの相乗平均。刻み 1/1000 秒の逐次インパルス法で、近づく速さ 0.05 m/s 以上の接触を出来事にする。sin・cos は自前（足し算・掛け算だけ）にして環境に依らず同じ結果にする。牌が倒れる・転がる音が要るようになったら、傾きを足す | |
| 部屋のモデル（5e）を reverb にどう写すか | **決定（5e）**：`seconds` = RT60（0.05〜10 秒に収める）、`decay` は T の半分で -30dB になる値（≒ 4.98。指数の減衰と半分の点で一致）、`wet` = 距離² ÷ (距離² + 臨界距離²)、`early` は直接音からの遅れと直接音に対する振幅の比（2 次まで 24 本）。早期反射の強さとインパルス応答の尾の釣り合いは、5c で録音して耳で確かめる | |
| 聞き比べの許容差（M2）と、変換の距離の許容（M4.5） | M2・M4.5 の途中 | 数字の差は目安にし、最後は耳で決める |
| 1 音あたりの大きさの目標 | M4.5 の前 | 3KB 以下（gzip 後）。ノード数の上限は M1 の同時発音数と合わせて決める |
| MCP の実装を mahjong-sensei と共有するか | M7 の前 | 写して始め、重なりが見えてから切り出す |

## 5. 危険と対策

| 危険 | 対策 |
| --- | --- |
| 形式が M2 で足りないと分かり、M1 をやり直す | M1 の段階で 16 音のうち 5 音（`discard`・`kan`・`win`・`riichi`・`rise`）を先に書いてみる。足りないものは早く見える |
| ランタイムが 10KB を超える | M0 から容量検査を CI に入れる。超えたら PR が落ちる |
| 物理エンジンが大きくなりすぎる | 5a は球・箱・平面・反発・摩擦だけ。転がりや複雑な形は 5d の後で必要になってから |
| 変換（M4.5）の効果が小さい・精度が出ない | M4.5 の 5 番（3 音の測定）で先に効果を測り、小さければ後回しにする。変換できないものは wav のまま配る（`sample` 層） |
| Web Audio の描画が Node とブラウザで違う | 数値の検査は「許容差つき」で書き、完全一致は純粋な compile の層だけで求める |
| 遅延の目標（20ms）が守れない | ランタイム内の処理を 2ms 以内とし、端末の遅延は測って表示するだけにする（提案書 3 章） |
